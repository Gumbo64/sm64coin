# SM64Coin v0.4: committed inputs, included proofs, proof-count fork choice

Status: **design**, branch `v0.4` (from tag `v0.3.0`). Nothing here is released.
The owner's decisions (2026-11-25) are recorded in section 7; the one thing still
open is the imitation-cost gate, which sets two parameters (the weight window and
the reward) when that measurement lands. Section 8 is the implementation plan and what is already
implemented on this branch.

v0.4 is **another chain reset**, like v0.3 (owner's decision, 2026-11-25): a new
genesis block, a new network id, heights restart at 0. There is no activation
height and no v0.3 code path to keep: every rule below applies from block 1.
v0.3 coins and blocks do not carry over.

What changes from v0.3:

| # | change | kind |
|---|---|---|
| 1 | **Committed inputs**: the proof's header commits the hash of the run's canonical inputs; the block id, `proof_id` and the signature use that hash; codecs become transport, negotiated between peers; a blob that doesn't decode to the committed hash is a *bad encoding*, never an invalid block | consensus + p2p |
| 2 | **Included proofs**: block h+1 carries the other valid signed runs for height h (same parent as block h, other keys), as self-contained proof records, up to a cap | consensus |
| 3 | **Proof rewards**: each included proof is paid a fixed share of new issuance in block h+1's coinbase, to the payout address its own template committed | consensus |
| 4 | **Fork choice**: longer **and** heavier, weight = blocks + counted included proofs; v0.3's 36-block reorg cap and equivocation penalty stay | node policy (deterministic from chain data) |
| 5 | **Evidence burn** (design only, optional): equivocation evidence included in a later block makes the equivocator's coinbase permanently unspendable | consensus, deferred |
| - | Pokes: **unchanged** (a poke overrides the whole pad: A/B/Z and the stick random, every other button released) | - |

Everything else (the 70-star cycle, the auction curve, the 20-minute target,
restarts, signatures, one run per key, publish-on-find with ω = 30 s, the
freshness bound, the replay queue, the 72-block coinbase lock) is v0.3's.

## 1. Committed inputs: encodings out of consensus

### 1.1 Why

In v0.3 the block id commits `proof_id(sm64_proof)`. For the stateless codecs
(0 raw, 1 run-length, 2 xz) that is a hash of the decoded run, but for the
state codecs (3 statectx1, 4/5 statemix) it is a hash of the **bytes**, because
decoding needs a replay. So:

- the state codecs are consensus: their models, their canonical-encoding check
  (`replay_state` re-encodes and compares) and any improvement (COMPRESS.md's
  mix2 + ring sticks, -20 %) are hard forks;
- a wallet that wants a block id must port `proof_id`, and for codecs 3-5 it
  would need the emulator; the web wallet ports a C++ copy of the stateless part;
- the tie-break size is the blob length for 3-5 and an RLE length for 0-2.

### 1.2 The proof blob (consensus)

```
sm64_proof = varint(frames) || start (1 byte: 0 parent, 1 power-on) || input_hash (32 bytes) || encoding
encoding   = codec id (1 byte) || codec body                     -- transport, not consensus
```

`input_hash` is the hash of the **canonical inputs** of the run:

```
input_hash = keccak256("sm64run2" || frames as u32 LE || start as u8 || pad_1 || ... || pad_n)
pad_i      = buttons u16 LE || stick x i8 || stick y i8          -- the input of the i-th NON-poked frame
```

This is byte-for-byte v0.3's `proof_id` of a stateless proof (`proof_id.rs`,
domain tag `sm64run2`), so the existing vectors (`web/wallet-wasm/test`,
`examples/proofid_vectors.rs`) and the Python port carry over. The inputs are
those of the non-poked frames only (`replay::Played::wanted`): poked frames are
regenerated from the seed and the game state, never stored, never hashed.

`proof_id(sm64_proof) = input_hash` read from the header: **no decoding**. A blob
whose header doesn't parse (truncated varint, unknown start byte, fewer than 32
hash bytes) keeps v0.3's fallback, `keccak256("sm64bad!" || blob)`, so it can
never share an id with a real run.

Unchanged on top of it:

- block id = `cn_fast_hash(hashing blob || proof_id || sm64_sig)` (`get_block_id_blob`);
- the signature signs `keccak256("sm64coin proof signature v1" || seed || proof_id || frames)` (`sign.rs`);
- equivocation evidence (`equivocation.rs`) compares `(proof_id, frames)`.

### 1.3 Verifying a committed proof (consensus)

1. The header parses, `frames >= 1`, `frames <= limit` (the time limit at the stamp, as v0.3), start rules as v0.3. These read only the committed header, so a failure is **Invalid**.
2. The signature verifies over `(seed, input_hash, frames)` (no decoding).
3. The encoding is decoded:
   - **stateless codec**: decode (zip-bomb caps as v0.3), hash; a decode error or `hash != input_hash` is **BadEncoding**. Cheap, before any replay.
   - **state codec**: decode frame by frame during the replay. The replay plays **all `frames` frames** even when the success condition appears early, hashing every decoded (non-poked) input, so the decoded run is known in full. `hash != input_hash` is **BadEncoding** whatever the replay saw. There is **no canonical-encoding check** any more: any encoding that decodes to the committed inputs is fine.
4. Only when the decoded inputs hash to `input_hash` does the replay's verdict count: the success condition must first hold on the last frame, every non-poked frame must have had an input, no input left over. A failure is **Invalid**: the committed run itself is invalid, whatever encoding carries it.

So: **Invalid** is said only about the committed run (and the header), and
every encoding of that run gets the same verdict. **BadEncoding** is said about
one blob and never about the block id.

### 1.4 BadEncoding in the daemon (node policy)

- The block is not marked invalid (`m_invalid_blocks`, alt-block storage, the replay queue's known-id set, `cache.rs`'s invalid-run memory: none of them records it). The run cache keys runs by `(parent, start, seed, input_hash)` for stateless encodings (hash-checked before the replay), and additionally by the body's bytes for state-coded ones, so a cache hit never vouches for an encoding nobody decoded: a node stores and relays only encodings it verified (tested: `tests/committed.rs`).
- The peer that sent it is dropped (an honest node verifies before it relays, and stores only blobs that verified, so a bad encoding is always the sender's fault), like forged evidence. The block is requested again from another peer.
- restricted `submit_block`: an error, the per-address invalid-proof penalty (`admit.rs`) applies as for an invalid proof (one replay was spent).
- Cost: a state-coded bad encoding costs one replay of at most `frames` (bounded by the limit, as an invalid claim does today); a stateless one costs a decode.

### 1.5 Codecs as transport (p2p, node policy)

- Codec ids become a **node-side registry** (`proof.rs` / `statecodec.rs`, versioned by node release). Adding or retiring a codec is a node release, not a fork. Registry rules (compression round 2, branch `compressor-research-2` 5c50446, `docs/COMPRESS2.md`): one-byte ids, **never reused**; each id has a **frozen decoder and golden vectors**; families: 0-2 generic (raw, run-length, xz), 3 statectx1, 4-5 statemix, **6-7 statemix2** (6 polar stick binarisation, best on miner runs: 2.44 bits/frame on the chain corpus against 3.44 today, with canonicalisation; 7 Chebyshev/square ring, best on human TAS runs), 8-15 reserved, 0xE0-0xEF experimental (never stored or relayed to peers that didn't ask). Integer-only decoders, about 260-320 k frames/s (the emulator is about 40 k). Nodes and miners encode best-of per run over the codecs they ship; v0.4's first release ships 0-7.
- **Baseline**: every v0.4 node decodes codecs 0, 1, 2 (stateless: no emulator needed to decode, so a node can always transcode to them).
- **Negotiation**: on connect each node sends `NOTIFY_SM64_CODECS` (levin `BC_COMMANDS_POOL_BASE + 13`): a list of `(codec id u8, codec version u8)` it decodes. A peer that sent nothing gets the baseline. When relaying a block (or a proof record, section 2) a node sends the smallest encoding it holds that the peer decodes, transcoding when needed (a node that verified a block knows its inputs, `Played::wanted`; encoding a state codec needs the replay states, so the verifier runs the encoders it ships alongside its verification replay and stores the smallest).
- **Storage**: the DB stores whatever encoding the node chose; the block id doesn't change.
- **RPC**: `get_block` returns the stored blob plus `sm64_input_hash` (hex) and `sm64_codec`; unrestricted RPC takes an optional `sm64_codec` to ask for a specific encoding.
- **Wallets** read `input_hash` from the blob header (bytes `[varint, start]` then 32 bytes): no decoder to port. The web wallet's C++ `proof_id` port shrinks to that.
- The 256 KiB parse cap on `sm64_proof` stays: a raw (codec 0) encoding of the longest valid run is 144 kB + 37, so a node can always fall back to raw.

### 1.6 The equal-length tie-break (node policy)

Inside the displacement window, between siblings of different keys with equal
frames: the smaller **canonical size**, then a **final key** that is a pluggable
node policy (`pof::TieKey`, `sm64pow_set_tie_key`): `SigHash` (v0.3's
`cn_fast_hash(sm64_sig)`, **the default** until the fairness research on tie-break
grinding reports), `SeedHash` (`cn_fast_hash(seed)`), or `FirstSeen` (no final key:
an exact tie keeps the block seen first). All nodes of a network should run the same
key, or exact ties can split them for a block.

- **Canonical size** = the length of the run-length layout of the committed run
  (`varint(frames) || start || 1 || runs`), the same for every encoding of the run:
  computed before the replay for a stateless encoding, noted by the replay for a
  state-coded one (`pof::note_size_of`; unknown until then, which never wins a tie).
- **Why a pinned encoder, and why run-length for now** (revisiting the codec-5
  choice): the measure must be the same at every node of every release, or exact
  ties split nodes. A best-of over the registry would change the measure whenever a
  release adds a codec (6-7 now, more later), so it is ruled out. Between pinned
  encoders: run-length is frozen code that every node already runs, costs nothing
  and needs no game state; statemix codec 5 (or 6) measures "simple, human-like
  inputs" better but needs encoding alongside the replay. The implementation uses
  run-length; switching the pin to codec 6 (the best on miner runs) is a small,
  node-policy-only follow-up if the owner wants compressibility rewarded more
  finely. Either way the pin changes only with a coordinated release.
- **Why it is pluggable** (fairness-research 96a2109, `V04.md`): near the difficulty
  floor most heights are exact ties, so the final key decides. The signature hash is
  grindable by the run's owner (equal-frame variants, re-signed): a compute-weighted
  lottery that favoured farms (a 30 % farm got 2.47x its share). The seed hash looks
  like one ticket per template, but it is grindable **before** any search, and more
  cheaply (a miner picks among template keys at about one hash and one scalar
  multiplication per key, microseconds), so it is not obviously better. First-seen
  is ungrindable but reopens the arrival races v0.3's deterministic tie-break closed
  (window-edge splits). The research on which to ship is running; the record order
  inside a block (`(frames, H(seed))`, section 2.4) is a consensus canonical order
  only and doesn't select which proofs get in (the includer does), so it is not affected.

## 2. Included proofs and fork choice

### 2.1 What a proof is

A **proof for height h** is a signed run that would be a valid block at height h
apart from the time limit: a template on the same parent as block h (`B_{h-1}`),
with its own miner key, whose run (replayed from `B_{h-1}`'s end state through
that template's pokes) makes the next point, plus its signature. They are the
near-best runs that lost the auction: a displaced block, a runner-up, any miner's
best run. For the maintainer's purposes they are **data** (many near-optimal
segments starting from the same end state, under different seeds) and,
counted in fork choice, a **measure of the compute behind a chain**.

### 2.2 The proof record (consensus wire format)

Self-contained, like v0.3's evidence (`template.rs`): a verifier needs no block
other than `B_h` and its parent's end state.

```
record     = varint(len) header       -- the proof's template block header (major, minor, timestamp, prev id, nonce)
           || varint(len) miner_tx     -- its coinbase, whole (the seed covers it; the key and the payout address are in its extra)
           || varint(tx_count)         -- the template's transaction count, coinbase included (>= 1)
           || branch                   -- depth(tx_count) x 32 bytes: the merkle branch of leaf 0 (the coinbase), section 2.3
           || varint(len) proof        -- a committed proof blob (section 1.2), any encoding
           || sig (64 bytes)
sm64_proofs (new block field, after sm64_sig) = varint(n) || record_1 || ... || record_n
```

Derived facts (`template::facts`, extended to a branch): `seed` (the hashing
blob with timestamp zeroed, from header, coinbase hash and root),
`key` (extra nonce `0x64 || key`), `payout` (section 3.2), `prev_id`, `height`.

The **leaf** of a record commits everything consensus reads, and nothing
re-encodable:

```
leaf = keccak256("sm64prf1" || seed || input_hash || frames as u32 LE || sig)
root = tree_hash(leaf_1 .. leaf_n)       -- Monero's tree_hash; n = 0: 32 zero bytes
```

`root` is committed by the including block's **coinbase extra nonce**
(section 3.2), hence by its seed and its block id. The record bytes are a
**witness**: the template header's timestamp (not in the seed) and the proof's
encoding can change in transit; a record set whose leaves don't give the
committed root is a **bad witness** (like BadEncoding: drop the sender,
refetch), never an invalid block.

### 2.3 The coinbase branch

Templates carry whatever transactions their builder's mempool had, so a record
carries a merkle branch instead of every tx hash (`template.rs` today: all of
them, up to 1024). Leaf 0 of Monero's `tree_hash` (which folds a
non-power-of-two count specially) is always present; the branch is the list
of sibling hashes from leaf 0 to the root (leaf 0 is always a left child):
`depth(1) = 0`, `depth(2) = 1`, and for n >= 3 with `c` the largest power of two
below n, `log2(c)` plus one when n is itself a power of two (Monero pairs leaf 0
at the first level only then). Implemented and tested against
`tree_hash` for every count from 1 to 70 (`records::coinbase_branch`,
`records::root_from_branch`). Typical SM64Coin templates have no other
transaction (branch empty).

### 2.4 Consensus rules for block h+1's records

For `B_{h+1}` with records `R_1..R_n` and its parent `B_h` (frames `F_h`, key
`K_h`, parent `B_{h-1}`):

1. `n <= CAP` (decided: 64). `n = 0` is always valid.
2. The leaves give the coinbase's committed root (else bad witness).
3. Each record: the template's facts parse; `height == h`; `prev_id == id(B_{h-1})`; the coinbase commits a valid miner key and a payout address.
4. Keys: every record's key differs from `K_h` and from every other record's key (**one proof per key**; a key that signed `B_h` is the winner, not a proof).
5. Order: strictly increasing by `(frames, cn_fast_hash(seed))`, the same ungrindable key as the tie-break (section 1.6). **One run counts once**: no two records, and no record and the winner, share an `input_hash` (identical runs on different seeds; runs are seed-bound, so this is all but impossible honestly).
6. Signature: verifies over `(seed, input_hash, frames)` with the record's key.
7. **Window, in auction time** (decided): a record is archivable iff it would have become valid at most `A` seconds after the winner's due time: `frames <= max_frames(d_h, due(F_h) + A)`, where `d_h` is block h's retarget difficulty, `due(F)` the first second after the parent at which a run of F frames fits the limit (`records::due_elapsed`), and `A = 60` (`records::window_frames`). Deterministic from the parent's difficulty and the winner's frames: no clock, and the stamps don't enter, so nobody can widen it by restamping; it follows any future change of the limit curve's slope by itself. At the equilibrium difficulty (about 2^16) 60 s is about +17 % frames. Also `frames <= max_frames_any` (36,000). No time-limit check: a proof is not a block.
8. Start: the natural start of height h: power-on iff `B_{h-1}` is the genesis block or ends the cycle, else the parent's end state. No restarts as proofs (all proofs of a height start from the same state: that is what makes them useful data).
9. Replay (section 1.3, same verdict kinds): valid run from `B_{h-1}`'s end state; BadEncoding of a record is a bad witness.
10. Coinbase payouts: section 3.

The records of height h can only be included by block h+1 (the next block).
Runs that miss it are lost to the chain (nodes may archive them as policy).

### 2.5 Which proofs count for weight

Weight counts the records within the **weight window**, defined the same way:
`frames <= max_frames(d_h, due(F_h) + W)`, default `W = 60` s (the window LATE.md
part 2 simulated: "eligible within ω = 60 s of the first eligible one"). `W` is a
**gate** (`records::Window::weight_seconds`): it may be narrowed, or turned off
(`None`: proofs weigh nothing, fork choice is v0.3's longest chain), from the
imitation-cost result.

### 2.6 Fork choice (node policy, deterministic from the chain)

`weight(B) = 1 + (records of B within the weight window)`; `W(chain above the fork point) = Σ weight`.

A node on chain M reorganises to chain A (both above their fork point) iff

```
len(A) > len(M)  AND  W(A) > W(M)                     -- "longer and heavier"
```

with v0.3's other rules unchanged: the 36-block reorg cap (`reorg.rs`) and its
operator override; the equivocation penalty (a tainted chain's length counts
1.5 blocks less, `equivocation::Policy::fork_choice`; proposal: a tainted block
also weighs 0); the displacement window and freshness bound decide same-height
siblings of a childless tip, as v0.3 (`pof.rs`). Ties keep the chain we have.

Measured (fairness-research `fair_fork.py`, re-run here with
`pow/tools/auction/headstart/v04_heal.py`, target 1200 s, 16 seeds x 200
trials, partitions 64 runs per cell):

| rule | P(z=6) 20 % | P(z=6) 33 % | P(z=24) 33 % | z(0.1 %) 20 / 33 % | 30/70 10 h | 50/50 3 h | 50/50 10 h | eclipse 10 h |
|---|---|---|---|---|---|---|---|---|
| longest chain (v0.3 without cap) | 0.071 | 0.398 | 0.150 | 26 / 147 | 0 % | 0 % | 0 % | 0 % |
| v0.3 (cap 36) | 0.071 | 0.388 | 0.128 | 26 / 37 | **100 %** | 0 % | **100 %** | **100 %** |
| weight alone | 0.027 | 0.336 | 0.014 | 11 / 43 | 0 % | 0 % | 0 % | 0 % |
| **longer AND heavier** | **0.000** | **0.029** | 0.000 | 5 / 13 | 0 % | 8 % | 28 % | 0 % |
| AND, heal at fork depth 18 (weight alone once both sides have 18 blocks) | 0.000 | 0.064 | 0.014 | 5 / 43 | 0 % | 0 % | 0 % | 0 % |
| AND, heal at depth 12 | 0.001 | 0.129 | 0.014 | 5 / 43 | 0 % | 0 % | 0 % | 0 % |

(Percentages in the partition columns are the runs still split 40 block times
after the rejoin; "10 h" partitions are 30 blocks deep, under the cap but the
blocks mined while split count too. The AND row reproduces LATE.md's.)

Reading it: "longer AND heavier" cuts the six-confirmation private-chain risk at
33 % from 0.39 to 0.03 and z(0.1 %) from 147 to 13. Its cost is convergence after
long, even (50/50) partitions: the two halves are level in length and weight
and neither dominates both for a while. The reorg cap then turns any partition
deeper than 36 blocks into a permanent split needing the operator (as in v0.3).
A **healing** rule (weight alone decides once the fork is D blocks deep on both
sides) converges every tested partition but gives back part of the attack
resistance (P(z=6) 0.064 at D = 18). Decided: plain AND, no healing (
partitions of hours are rare and loud; the cap already needs an operator beyond
36 blocks) or AND + heal at D = 18.

Near the difficulty floor (fairness-research `V04.md`) proof weight is essential:
the private chain's P(z=6) at 33 % is 0.62 with longest-chain and 0.000 with
"longer AND heavier".

**The displacement window ω** (v0.3: 30 s, `rules::POF_WINDOW_SECONDS`) is a
parameter. At a 20-minute target ω = 30 s sits at SM1 break-even (LATE.md
part 2 (c)); the smoothness research preferred 30 s against sniping and tip
flips. With proof weight on, a larger ω no longer opens the private-chain attack
(P(z=6) stays at or below 0.01 for ω 90-360 s with "longer AND heavier"), so ω can
be raised for SM1 margin; revisit ω (and the archive/weight windows, which are
measured from the winner's due time, not from ω) once proof weight is live.

**The limit curve's slope stays fixed** (one difficulty halving per 60 s): an
adaptive slope was simulated and rejected (it destabilises the retarget).

Implementation note: the daemon's reorganise hook (`Blockchain::sm64_fork_choice`)
already hands Rust the seeds of the blocks above the fork point; it will also
hand each block's counted proofs (Rust counts them when it verifies the block
and keeps them by id; the alt-chain walk is at most 36 deep).

## 3. Proof rewards and emission

### 3.1 Formula (consensus)

`R(h) = (MONEY_SUPPLY - generated) >> 14` (v0.3's base reward, with v0.3's tail floor).

- The block's miner: `R(h) + fees`, **unchanged** (the includer's reward does not depend on the proofs it includes).
- Each of the n included records (archive window): `r(h) = min(R(h) / D, R(h) * POT / 100 / n)` atomic units, extra issuance, decided D = 128 (0.78 % of R each); **POT** (a parameter, proposed 25 %) bounds the total: fairness-research `V04.md` found a total proof pot of about 10-25 % of the block reward about proportional near the floor and 50 % over-correcting. With D = 128 and POT = 25 the pot binds above 32 proofs. Both are gates (`records::PROPOSED_REWARD`; `divisor: None` pays nothing, `pot_percent: None` leaves the total at `n R / D`), to be confirmed by the imitation-cost result.
- Above the pot's threshold the per-proof amount falls with n, so an includer that also holds a proof gains a little by excluding others' (it keeps the pot among fewer proofs); below it there is no such gain. With weight on, exclusion still costs the includer weight. Keep the threshold above the usual proof count (32 at the proposed values).
- Coinbase total = `R + fees + n * r`; `generated` grows by that, so Monero's curve (`remaining >> 14`) absorbs the extra issuance by itself: proofs make the main emission run slightly faster, they don't change the supply schedule's limit or the tail.

Emission per day (72 blocks): `(1 + min(n̄ / D, POT))` times v0.3's in the main-emission phase, where n̄ is
the mean number of included proofs. With D = 128: n̄ = 8 → +6 %, n̄ = 16 → +12.5 %,
the cap n = 64 → +25 % with the pot (+50 % without it). Alternative
(not chosen): keep emission per day constant in expectation by cutting the
miner's share to `R * (1 - n_target / D)` whatever n is (no exclusion incentive,
since the cut doesn't depend on the block's actual n); with n_target = 8, the
miner gets 93.75 % of R.

Why not split a fixed pool among the proofs, or pay proofs out of the includer's
reward: a pool split lets an includer that also holds a proof exclude the others'
to take the whole pool, and paying from the includer's reward makes exclusion
profitable. A fixed amount per proof from new issuance makes inclusion free for
the includer and, with proof-weight fork choice, profitable (heavier chain).

### 3.2 Where the payout goes (consensus)

A template's coinbase pays a one-time output key: it doesn't reveal an address,
and a later block can't pay "the same address" with it (Monero derives an
output key from the tx key *and the output index*; the same key at another
index is not recognised by a wallet). So a v0.4 template **commits its payout
address explicitly** in the coinbase extra nonce, which the seed covers:

```
extra nonce (v0.4) = 0x64 || miner key (32)                          -- v0.3
                   || TLV*: tag u8 || len u8 || value                 -- v0.4, unknown tags ignored, pools may add their own
   tag 0x01, len 65: payout = flag (0 standard address, 1 subaddress) || spend public key || view public key
   tag 0x02, len 32: the included-proofs root (section 2.2); omitted when n = 0 (then the root is the zero hash)
```

`get_block_template` fills both from its `wallet_address` and its proof pool;
miners pass only the key (as in v0.3). The extra nonce stays under Monero's
255-byte limit (33 + 67 + 34 = 134).

Block h+1's coinbase: output 0 (and any further miner outputs) first, then
output `j = m + i` (m = number of miner outputs, committed as the count of
outputs before the first proof output: proposal m = 1 exactly) pays record i:

```
r_j    = H_s("sm64coin proof payout v1" || leaf_i)          -- public and deterministic: anyone can check the output
R_j    = r_j * G (standard)  or  r_j * D_i (subaddress spend key D_i)      -- in tx_extra_additional_pub_keys[j]
deriv  = 8 * r_j * A_i                                       -- A_i: the view key of record i's payout
P_j    = H_s(deriv || varint(j)) * G + B_i                   -- B_i: the spend key; standard Monero output derivation
view tag = keccak256("view_tag" || deriv || varint(j))[0]
amount = r(h+1), in clear (coinbase)
```

Every validating node recomputes `P_j`, the view tag, `R_j` and the amount.
Because `r_j` is public, anyone can see that output j pays record i's address:
that is already public in the record, and nothing else is revealed (the miner's
own output keeps a private tx key). Wallets need **no change**: wallet2 already
scans coinbases with additional tx public keys through the normal
`process_new_transaction` path (checked: the miner tx goes through it,
`wallet2.cpp:3054`), and subaddress payouts work as for any transfer.
Privacy note for miners: a record links its proof to an address; the miners
should use a fresh subaddress per template (default in miner software).

Coinbase size: about 75 bytes per proof output (key, view tag, amount, additional
key), 4.8 kB at n = 64. `template.rs`'s `MAX_MINER_TX` (4096) rises to 16 KiB.

### 3.3 Timing

The template for h+1 is built after height h settles: after the displacement
window (ω = 30 s) closes on h, plus a short collection grace (decided:
10 s): honest miners already wait for the window before building on
a block. The proof set is frozen in the template (the root is in the seed).
Proofs arriving later can't be added without a new template, which is a new key
and a new search; miner software won't. A proof's author therefore publishes it
as soon as block h is known and its run cannot displace it (it is longer, or the
window is closed), so it propagates within the window.

## 4. Incentives, farming and imitation

- **Each proof needs a real search.** A proof is a valid run under its own template's pokes. Sybil keys don't help: keys are free, runs aren't, and one proof per key means one run per template. A proof signed twice is equivocation (v0.3 evidence works on records, since they carry signatures).
- **Inclusion is free and profitable** for the includer (section 3.1); exclusion costs it weight and gains it nothing.
- **Publishing is free** for the prover (it already holds the run) and earns `r`. Today a runner-up publishes nothing (SMOOTH.md: 1.1 claims per height); with v0.4 every miner within P % publishes: that is the data the owner wants.
- **Fairness** improves for small miners: a miner that finds a good run but rarely the best still earns `r` per height it lands within P %. That pays roughly per search, not per win, smoothing income (FAIRNESS.md's cliff at ~1.5x the block interval moves out for proof rewards, since a proof is judged by length, not by being first).
- **Imitation risk** (a separate agent is measuring it, branch `imitation-cost`, not finished at the time of writing): once block h is published, its run is public. If adapting that run to a fresh template (new pokes) is cheap, a farmer can mint proofs: K templates, K imitations, K x r, and an attacker can stuff its private chain's blocks with imitations of its own winners (it holds them early: its runs are private until it publishes). Effects:
  - On weight: "longer AND heavier" never makes an attacker better off than longest-chain (it must still be longer), so the worst case is v0.3's security. But a stuffed attacker chain can be *heavier* than the honest chain, and a node eclipsed onto it would not switch back to a longer honest chain that is lighter (it needs both): an eclipse becomes sticky. The healing rule would make stuffing win outright at depth D. So **the healing rule is safe only if imitation is expensive**.
  - On rewards: farming inflates emission up to `CAP * r` per block and dilutes nothing else (fixed r).
- **The fallback** the owner suggested ("count only proofs due before the winner could have been seen") cannot be a clock rule in consensus. Its deterministic form is a tighter length window: a proof is due before the winner is seen iff it is (nearly) no longer than the winner, so the rule becomes a weight window of `W = δ` seconds of auction time, δ the winner's publication lead plus propagation (5-10 s). It works exactly when imitations come out systematically longer than the original by more than δ, which the imitation measurement gives directly (guided-search lengths vs independent ones). Decision table (**OPEN**, to settle when `imitation-cost` reports):

| imitation cost of a within-window proof | weight window | rewards | healing |
|---|---|---|---|
| expensive (>= ~50 % of a fresh search) | W = 60 s | D = 128 on all included | allowed |
| moderate (10-50 %), or imitations land > δ later | W = δ (5-10 s) | only weight-window records; D = 256 | no |
| cheap (< 10 %) and as short as the original | weight off: v0.3 fork choice (longest + cap) | off, or a token D = 1024 | no |

In every row the records stay in the chain as data; only their weight and pay change.

## 5. Evidence burn (design only; optional, not in the first v0.4 cut)

v0.3 left "a consensus burn of the equivocator's locked coinbase" in reserve.
With the 72-block coinbase lock it can be made convergence-safe:

- A block may include **evidence records** (`equivocation.rs` wire format: the 272 bytes plus the accused template, already self-contained) in another new field, committed by a third TLV in the extra nonce (tag 0x03, a root of their hashes).
- Valid evidence about block `B_k` **in this chain** (its seed, its committed key), included at height `<= k + 36` (before the 72-block lock ends, with margin), **burns** `B_k`'s miner outputs (outputs before its first proof output; the provers' outputs it paid are theirs and stay).
- "Burned" = permanently locked: `Blockchain::is_tx_spendtime_unlocked` returns false for them forever. Monero already refuses any ring with a locked member (`check_tx_inputs` -> `is_tx_spendtime_unlocked` for every ring member, `blockchain.cpp:3911`), so a burned output can never be spent **or used as a decoy**, and since it never unlocked, no existing transaction can reference it.
- Wallets: `get_outs` reports `unlocked=false` for it (`Blockchain::get_outs`, `blockchain.cpp:2327`) and wallet2 drops locked decoys (`wallet2::tx_add_fake_output`: `if (!unlocked) return false`, `wallet2.cpp:9293`), requesting extra outputs beyond the ring size (`base_requested_outputs_count`), so honest wallets never pick it. **Checked: wallet2 honours the flag.** The output distribution still counts it (wallet2 picks it with negligible probability and drops it). The web wallet's decoy code must be checked the same way.
- Why it is safe where "permanently invalid" was not (LATE.md part 3, the "evidence bomb"): the block stays valid and the chain doesn't move; only money is lost, inside the lock, decided by the evidence the chain itself carries. Burn state must be undone on reorg (it is derived from blocks in the last 72; recompute on pop).
- What it adds over v0.3's fork-choice penalty: it takes the reward even when the equivocator's chain wins.

## 6. DoS, replay cost, sync, block size

Numbers: a proof is about one winning-run length, ~2,500 frames at the
retarget's equilibrium (V0.3-NEW-CHAIN.md); the archive window bounds it at
about `1.17 x F_h` (+60 s of auction time at equilibrium). Raspberry Pi: 5.6 k frames/s per core (owner's figure; DOS.md had an
estimate of 2.5-3 k), x86: 36-48 k frames/s per core.

| | typical (n = 10, 2,600 frames) | worst case (n = 64, 2,950 frames) |
|---|---|---|
| frames per block (block + proofs) | 28.6 k | 191 k |
| Pi, one core | 5.1 s | 34 s |
| Pi, 4 cores (proofs are independent, same parent state) | 1.3 s | 8.5 s |
| x86, 4 cores | 0.18 s | 1.2 s |
| sync, one year (26,280 blocks), Pi 4 cores | 9.3 h (v0.3: 50 min) | 62 h |
| sync, one year, x86 8 cores | 0.6 h | 4 h |
| block size (records, state codec ~1 kB/run, template ~0.4 kB) | ~15 kB | ~90 kB plus 64 template coinbases of up to 4.8 kB each (~400 kB; they repeat each other's proof outputs and compress well in transport) |
| coinbase | +0.75 kB | +4.8 kB |

Design consequences:

1. **Proof gossip ahead of the block.** Records are relayed on their own (`NOTIFY_SM64_PROOF`, levin `+ 14`) as soon as block h is known, verified (replayed) once, cached by `(seed, input_hash)`, kept in a per-parent **proof pool** (best CAP by `(frames, input_hash)`, plus a margin). When `B_{h+1}` arrives, its records are cache hits: the block itself costs one replay, as in v0.3. This is what keeps the 30 s window and relay latency unchanged (relay after replay, v0.3).
2. **Proof relay DoS** follows the claim rules (DOS.md): cheap checks first (parse, facts, height = our tip's, prev = our tip's parent, key distinct, signature, window vs our tip's F; 0.2 ms), per-source budget, replay queue (proofs rank after blocks, shortest first, known sources first), invalid → source refused (doubling), at most `2 x CAP` proof replays per parent per node. A displaced tip block becomes a pool record at no cost.
3. **A block's records are replayed in parallel** from one parent state; the block's own run first; abort at the first invalid. An includer that stuffs invalid records needs a winning run to make nodes try (real work), and loses the block.
4. **Sync**: the pre-pass (`preverify`) replays records in parallel with blocks. Optional node policy (decided: opt-in): `--sm64-assume-valid <block id>` skips replaying the *records* (not the blocks) below that block, still checking structure, root, signatures and payouts, like Bitcoin's assumevalid; it trusts that checkpoint for rewards and weight. Recommended for the Pi.
5. **Size caps**: `sm64_proofs` field at most 2 MiB (raw fallback worst case: 64 x (12 kB raw + 5 kB template) = 1.1 MB); per-record template caps as `template.rs` with `MAX_MINER_TX` 16 KiB, branch depth <= 10.

## 7. Decisions (owner, 2026-11-25)

1. **Imitation-cost gate**: build now, gate later. The weight window (`weight_seconds`) and the proof reward (`PROPOSED_REWARD_DIVISOR`) are parameters, set from the `imitation-cost` measurement when it lands (section 4's table, with the windows read in seconds of auction time). **Still open.**
2. **Cap**: 64.
3. **Archive window**: auction time, +60 s after the winner's due time (section 2.4 rule 7).
4. **Weight window**: the same definition, default +60 s, a gate.
5. **Reward**: extra issuance, `R / 128` per included proof, the miner keeps its full reward.
6. **Healing**: none (plain "longer AND heavier", the 36-block cap and the operator override).
7. **Equivocated block**: weight 0, plus v0.3's 1.5-block length penalty.
8. **Proof collection grace**: 10 s after the window closes.
9. **Evidence burn**: later.

## 10. Isolation and staging

Owner's guidance: every consensus change is isolated and independently switchable.

**Switches** (`pow/sm64pow/src/features.rs`, process-wide, set once at start-up for the network;
defaults: all on):

| switch | what it turns on | depends on | off means |
|---|---|---|---|
| `committed_inputs` | the committed proof header, `proof_id` = input hash, BadEncoding (section 1) | - | v0.3's proof layout and `proof_id`, the canonical-encoding check |
| `included_proofs` | proof records in blocks (section 2.2-2.4) | committed inputs | a block's record set (and its root) must be empty |
| `proof_weight` | "longer AND heavier" (section 2.6) | included proofs | v0.3's longest chain (with the taint penalty) |
| `proof_rewards` | payouts to included proofs (section 3) | included proofs | proofs are not paid |

`Features::valid` enforces the dependencies. Every switch is covered on and off by
`tests/features.rs` (its own process). The dispatch points are few and named: `proof_id::active`,
`proof_id::claimed_frames`, `chain::{verify_any, rebuild_any, played_any, prepare_any}`,
`pof::canonical_size`, `mining::{seal_proof_at, seal_proof_state_at, decode_proof_any}`, the FFI
proof-blob functions, `records::{check, prefer_alt, proof_reward}`.

**Node policy, not switches**: the tie-breaks (section 1.6), the codec registry (1.5), the
windows' widths (archive / weight seconds), the pot and the divisor, ω, the collection grace,
assume-valid.

**Proposed staging** (each stage can be its own reset release, or stages can be combined; the
owner decides):

- **Stage A: committed inputs only** (`Features::STAGE_A`). The smallest change: encodings leave
  consensus (codecs 6-7 ship as node policy), wallets read the hash, bad encodings stop being
  invalid blocks. No new block field, no coinbase change. Monero side: `proof_id` reads the
  header, BadEncoding handling (`-3` from verify, `4` from the queue), new network ids and
  genesis.
- **Stage B: included proofs as data** (`Features::STAGE_B`): the `sm64_proofs` field, the
  extra-nonce TLVs (payout, root), the proof pool and gossip, record replays. No weight, no
  rewards: nothing about security or emission changes, the chain just archives the near-best
  runs.
- **Stage C: weight and rewards**, gated on the imitation-cost result: `proof_weight` and
  `proof_rewards` (each alone is valid too), with the windows and the pot set from that
  measurement.

Implementation order: stage A end to end first (sm64pow daemon path: done; the Monero hooks and a
private network: next), then B, then C.
