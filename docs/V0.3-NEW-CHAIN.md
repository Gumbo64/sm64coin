# SM64Coin v0.3: a new chain with signed proofs

v0.3 starts a **new chain**: a new genesis block and a new network identity.
The v0.2 chain is not continued; its coins and blocks don't carry over.
There is no activation height and no old-rule code path: the new rules apply
from block 1. What changes from v0.2:

- **consensus**:
  - **signed proofs**;
  - a **20-minute block time** (v0.2: 5 min), with emission per day unchanged;
  - restart delays scaled with it;
  - a **72-block coinbase lock** (24 h; v0.2: 4 blocks);
- **relay and fork-choice policy**:
  - **publish-on-find** with a 30 s **displacement window** (equal lengths:
    the lower signature hash);
  - the **equivocation rule**, with self-contained evidence and a
    **fork-choice penalty** for chains holding an equivocated block;
  - one block per run: restamped copies converge on the **earliest stamp**;
  - a 60 s **freshness bound**;
  - the **replay queue** ([DOS.md](DOS.md)).

The parameters are in one marked place: `STAR_CYCLE`'s "v0.3 CHOSEN
PARAMETERS" block and the constants below it in `pow/sm64pow/src/rules.rs`.

The reasons are in the fairness research, `pow/tools/auction/headstart/FAIRNESS.md`
on branch `fairness-research` (9ce5c91).

## Why

Every SM64Coin block's run can be changed a little and still be valid. Flip
or drop the proof's last byte and the last 1-13 inputs differ, but the star
still lands on the same frame. The seed does not cover the proof, so the
variant is a valid block with a new id. On the v0.2 mainnet **all 34 blocks**
have such a variant among the four cheapest edits (73 of 136 edits are
valid). [DOS.md](DOS.md) has the measurements.

v0.2.9's relay policy (`admit.rs`) stops variants from costing nodes replays.
Two problems are left, and no relay policy can fix them:

- **Fork-race griefing.** Anyone who sees block A first can race a free
  variant A' to some miners and split the network for a block.
- **A fork rooted at a variant** that spans more than one sync batch does not
  reorganise ([DOS.md](DOS.md), "What is left" 3).

Signing removes both at the root, because only the miner can make another
valid run for its template. The fairness research found that the
alternatives either don't help or make things worse:

- Content-based tie-breaks (lowest pads, fewest buttons, lowest hash) are
  grindable by spamming variants.
- Slow decay was measured and rejected.

See `pow/tools/auction/headstart/RESULTS.md` and `SLOWDECAY.md` on the
research branches `headstart-research` / `headstart-research-slowdecay`.

The owner chose a chain reset over an activation height. One coordinated
restart is simpler than carrying two rule sets forever.

## What changes

### Signed proofs (consensus)

1. **The miner key goes in the coinbase.** For each template, the miner
   generates a throwaway key pair. This is Monero's key format, an ed25519
   scalar and point, and is never the wallet's spend key. The miner asks
   for the template with `get_block_template {"wallet_address": ..,
   "extra_nonce": "64" + hex(public key)}`.
   - The daemon writes the nonce into the coinbase `tx_extra` as a
     `TX_EXTRA_NONCE` field. This is Monero's existing mechanism; pools use
     it for worker nonces.
   - The first byte `0x64` tags the content as a miner key, followed by the
     32-byte key. Pools may append more bytes.
   - `reserve_size` must be 0 or omitted, because Monero refuses both.
   - The seed is `cn_fast_hash` of the hashing blob with the timestamp zeroed.
     The hashing blob contains the merkle root, which covers the miner tx and
     its extra. So the seed, and with it the pokes, already commits the key:
     **one template, one key**.
   - The key must therefore be chosen before the run is played, and the same
     extra nonce must be used for every template request belonging to that
     run.
2. **The block carries a signature.** The new last field of the block blob is
   `sm64_sig`, 64 bytes. It is a Monero signature (`crypto::generate_signature`
   / `check_signature`: Schnorr on ed25519 with Keccak, `c || r`) by the
   coinbase key over:

   ```
   keccak256("sm64coin proof signature v1" || seed || proof_id(sm64_proof) || frames as u32 LE)
   ```

   `frames` is the proof header's claimed length.
3. **Nodes check it before any replay** (`chain::verify_signed_block` /
   `sm64pow_verify_signed_block`). The block is **invalid** if any of these
   holds:
   - the coinbase's first extra nonce does not commit a valid key (canonical,
     not small order, torsion-free);
   - the signature does not verify (both scalars must be canonical, and `c`
     non-zero);
   - the signature signs another seed, proof or length.

   The check takes about 0.1-0.2 ms, most of it `proof_id` (it decodes a
   stateless proof), and no replay. The sync pre-pass stops at the first bad
   signature. A held block's signature is checked before it can displace a
   held run of the same template.

Design decisions:

| question | decision | why |
|---|---|---|
| key type | Monero's own Schnorr signatures, byte-compatible with `crypto::check_signature`; implemented in Rust (`pow/sm64pow/src/sign.rs`, curve25519-dalek + Keccak) | No new signature scheme and no new C++ dependency: consensus stays in Rust, and stock Monero code can check the same signatures. curve25519-dalek is pure Rust and already in the workspace (the leaderboard), so the browser miner signs in WASM. The Python SDK has a pure-Python port, with no new dependency. |
| strictness | canonical `c` and `r`, `c != 0`, commitment not the identity; key canonical and torsion-free | A third party can't turn a valid signature into another valid one (`r + l`), so it can't mint a new block id. The miner picks its key, so the strict key rules cost honest miners nothing. |
| signing nonce | deterministic: `k = reduce512(keccak512("sm64coin signing nonce v1" ‖ secret ‖ msg ‖ ctr))` | Re-signing the same run gives the same signature, so the same block id. No RNG is needed at signing time. Verification doesn't care how `k` was chosen. |
| what is signed | seed, `proof_id`, frames | The **seed** binds the signature to the template, timestamp excluded, so restamping a block keeps its signature. **`proof_id`** is what the block id already commits to, and it is unchanged when the daemon re-encodes a stateless proof at `submit_block`, which signing the raw bytes would break. **Frames** let equivocation evidence compare lengths without the proofs. |
| key location | the coinbase extra nonce (`0x64` ‖ key), not a new `tx_extra` tag | Monero already lets a miner choose it (`get_block_template extra_nonce`), so it needs no change to Monero's tx-extra parser or the template RPC. The daemon's computed seed already covers it. |
| signature location | a new block field `sm64_sig` after `sm64_proof`, not inside the proof blob | The proof format, codecs, `proof_id` and their test vectors are unchanged. The signature is visible on its own in JSON (`"sm64_sig"`), and the fixed size leaves no length games. |
| in the block id? | **yes**: id = `cn_fast_hash(hashing blob ‖ proof_id ‖ sm64_sig)` | Third parties can't change the signature, and honest re-signing is deterministic, so including it creates no new ids. Excluding it would make it a witness. Then a garbage-signature copy would share the honest block's id, which risks poisoning id-keyed caches: "already have", invalid-block lists, requested-object tracking. |
| key per template | automatic, throwaway, generated by the miner | It is not the wallet key, so a leaked key costs nothing beyond that template. |

**Group mining** (the `group-mining` branch, not merged): the leader
generates the template key and shares the **secret** with its full-trust
group, so any member can sign and submit a run for the group template.
- Rust SDK: `run_miner_keyed(bot, cfg, &mut |round| Ok(Keypair::from_secret(&shared)?))`.
- Native miner: `Daemon::template_for(address, key)`.
- Python: `Keypair(secret)` passed as `next_key` to `run_miner`.
- Web: `minerkey.js` takes a key object.

The group branch needs these calls:
1. Leader: `Keypair::generate()`, then `get_block_template` with its
   `extra_nonce`.
2. Leader: share `{template blob, seed, secret}`.
3. Member: `sign_proof(key, seed, proof)`, then `seal_block`.

Members must never sign two different runs of the same length (see below);
the group should agree on one submitter.

### The new block field

```
block blob = header || miner_tx || tx_hashes || varint(len) || sm64_proof || sm64_sig (64 bytes)
```

- Templates and the genesis block carry 64 zero bytes. A template blob
  therefore ends with `00` (the empty proof) plus 64 zero bytes.
- To seal, strip those 65 bytes, set the timestamp, and append
  `varint(len(proof)) || proof || sig`. The helpers are
  `sm64pow::mining::seal_block` (Rust), `sm64coin.daemon.seal` (Python) and
  `web/src/lib/block.js seal` (JS).
- `proof_id` itself is unchanged, and so are its vectors in
  `web/wallet-wasm/test`.
- Block ids change, because they now commit to the signature.
- Seeds are computed the same way, but every template now has a different
  one, because each contains its miner key.

### The equivocation rule: one run per key (relay policy, `pow/sm64pow/src/equivocation.rs`)

With signing, "same key" and "same template" (same seed) are the same thing.
**A miner key signs at most one run per template.** Any two different signed
runs under one key/seed (another `proof_id`, or another length) are
equivocation evidence. There is no length comparison, no "a shorter run
replaces the held one", and no `LONGER_IS_EVIDENCE` switch: shorter, equal and
longer second runs are all evidence, whether or not either block is valid yet.
The same run sent again (same `proof_id` and length) is a duplicate, not
evidence. **Restamped copies are one block with a deterministic choice**:
the timestamp is not signed, so anyone can restamp a published block within
its validity (a new block id, same run, same coinbase) and race the copy to
some miners (review finding 4). Nodes treat copies of one run as one block
and prefer the **earliest stamp, then the lowest block id**: a node holding a
later copy switches to the preferred one while it is childless and inside
the displacement window (`pof::restamp_preferred`, `Policy::displaces`), and
never prefers a later restamp. Every node ends on the same copy; the miner's
reward is the same either way.

What a node does:

- The first signed run it sees for a seed is the template's **claim**
  (`Policy::claim`, called on arrival and again when a block is verified).
  It goes through the normal path: queued until due, replayed, accepted.
- A second, different signed run for that seed is **not replayed and not
  relayed as a block**. The node keeps compact **evidence**: 272 bytes (tag,
  seed, key, two `(proof_id, frames, sig)`), verifiable without the blocks,
  logs it, and relays it (`NOTIFY_SM64_EVIDENCE`). Nothing is done to the peer
  that relayed the second run (an honest node may relay either).
- **The first run stays as it was.** It is held or queued as normal and
  accepted when due. Once the template has evidence, the node refuses to build
  on that template's block **while it is childless**: `get_block_template`
  without `prev_block` builds on a clean sibling at the tip's height, or else
  on the tip's parent (`choose_parent`, `Policy::avoid`). The equivocator's
  block then loses the race once a sibling gets a child. This is the old rule,
  applied to the template instead of to the equal-length case.
- A second run for a template whose block is already in our chain (after a
  restart, when the claims are forgotten) arrives as an alternative block and
  is judged the same way (`judge_sibling`, from `sm64_skip_alt`).
- Consensus is unchanged: a block is never invalid for equivocation, so a sync
  batch that carries the second run still verifies. Evidence counts against a
  template only if its key is the one that template's coinbase commits (a node
  records the key when it checks a signature), so evidence forged over
  someone else's seed does nothing.

**Why one run per key.** The earlier rule let a miner submit any number of
strictly shorter runs before its block was valid, each replacing the held one.
That made nodes keep and compare several runs per template and made "when is a
second run misbehaviour" depend on lengths and timing (an honest A-then-A'
pattern could look like equivocation to a third node). A miner that wants
improvements does not need that: it keeps its improvements private and
publishes its best run once, a few seconds (default 5 s) before it is due.
Security does not come from early publication. It comes from due-time
eligibility (a run only counts once it fits the time limit), the omega = 30 s
displacement window (a strictly shorter run of *another* key displaces our
block inside the window), and honest miners waiting for the window before
building on a block, and none of those needs a run to be public before it is
due. The rule also makes the DoS surface smaller: one replay per template, a
second claim costs the node 0.2 ms (the evidence check).

**The evidence message**, `NOTIFY_SM64_EVIDENCE`, levin id
`BC_COMMANDS_POOL_BASE + 12`, one `std::string evidence`: the 272 bytes
above followed by the **accused template** (`template.rs encode`: the block
header, the coinbase transaction and the block's other tx hashes; a few
hundred bytes, at most `equivocation::MAX_WIRE`). It is **self-contained**:
a node recomputes the template's seed (merkle root over the coinbase and the
tx hashes, timestamp zeroed) and reads the miner key from the coinbase's
extra nonce, so it verifies evidence about a block it has never seen, and
evidence over someone else's template with the attacker's own key fails
(review finding 3: keyed by seed alone, first come, it could pre-empt the
real evidence).
- A node that finds equivocation (the daemon handles every block inside a
  `block_scope`, so the evidence gets that block's template) or receives new
  valid evidence queues it (`take_outbox`); `core::on_idle` relays it to
  every public peer.
- It is also **sent along with the accused block** whenever that block is
  relayed (`core::sm64_relay_evidence_for`), and to every **newly connected
  peer** for accused blocks within 8 heights of the tip (protocol `on_idle`).
- Recent evidence (the last 64, with its fork-choice flag) is **kept across
  restarts** in `sm64_evidence.bin` in the data dir.
- The handler drops messages of the wrong size; Rust verifies the rest
  (`sm64pow_evidence_received`), with a per-peer rate limit (a burst of 16,
  then 8 a minute). **Forged evidence drops the peer.**

**Fork choice with the equivocation penalty** (node policy, not consensus;
`equivocation::Policy::fork_choice`, the hook `Blockchain::sm64_fork_choice`
in the reorganise condition). From the fairness simulation
(`fairness-research`, LATE.md): an equivocator mining on its own avoided
block with a head start wins the fork 67-75 % of the time, so
self-equivocation selfish mining pays from alpha about 0.3, and "avoid for k
descendants" makes it worse. What removes it (share 0.003 at alpha 0.4): a
chain whose blocks above the fork point include an equivocated block weighs
**1.5 blocks less**. So an equivocated chain needs a lead of 2 to win, and a
clean chain of equal length, or one block shorter, beats an equivocated one;
otherwise the longer chain wins and a tie keeps ours. It is symmetric and
deterministic given the same evidence. **Late evidence is bounded**: evidence
counts for fork choice only if this node had it while the accused block was
at most 2 deep (`FORK_CHOICE_DEPTH`); evidence that surfaces later is still
kept, relayed and used by `choose_parent`, but can't move fork choice, so it
can't be used for a deep reorg.

A reserve option, not implemented: a consensus burn of the equivocator's
locked coinbase, via evidence included in a later block.

### The 20-minute block (consensus)

`Rules::target_seconds` is 1200, and so are `DIFFICULTY_TARGET_V1` / `_V2`
(v0.2: 300).

Why: FAIRNESS.md section 0 and section 5.
- What decides who wins is the latency of one search, which is 18-106 M
  emulated frames with a hard floor of about 18 M.
- A miner earns its share while its mean search time is under about 1.5× the
  block interval, and gets nothing beyond about 2×.
- At 300 s only multi-thread native searches are fair (about 250 s on 4
  threads). One-thread natives take about 860 s and browser workers about
  1700 s, and both earn 0.
- A longer target is the only rule lever that moves this cliff: 600 s makes
  one-thread natives fair, 900-1200 s browsers. A grace period does not: it
  is either a longer block or nothing.
- Per-block security is unchanged.

What follows from it:

| | v0.2 (5 min) | v0.3 (20 min) |
|---|---|---|
| emission per block | `(supply − generated) >> 16` | `>> 14`, 4× per block, **the same per day**. Monero's factor `20 − (minutes − 1)` doubles per extra minute; at 20 min it would be 1, half the supply in one block, so the fork sets 14 explicitly (`get_block_reward`, with a `static_assert` on the target). The tail emission is per minute, so it is unchanged per day |
| coinbase unlock | 4 blocks ≈ 20 min | **72 blocks = 24 h** (`CRYPTONOTE_MINED_MONEY_UNLOCK_WINDOW`; about Bitcoin's wall-clock maturity, and room for a future evidence-burn rule; only the genesis coinbase carries 10) |
| wallet spendable age | 10 blocks ≈ 50 min | **3 blocks = 1 h** (`CRYPTONOTE_DEFAULT_TX_SPENDABLE_AGE`) |
| restart delay | 1 h + 60 s/point, at most 2 h (12 block times) | **4 h + 240 s/point, at most 8 h** (still 12 block times, so a slow network with difficulty pinned at 1 doesn't throw its progress away; **open**: 4 h is a long stall) |
| limit curve | `decay_grace` 0, `decay_halving` 60 s, `start_halvings` 20, cap 36,000 frames (20 min of play), floor 600 | **unchanged**; FAIRNESS.md section 9 and SLOWDECAY.md, and the "no grace" test is kept |
| what the retarget settles at | difficulty ~2^4-2^8 | ~2^16 for ~2,500-frame winning runs: where the shortest finished run fits about 1,200 s after the parent. At difficulty 1, a network too slow for its target, the limit reaches its 20-minute cap exactly one target after the parent |
| locked-tx deltas, wallet time estimates, the block-rate warning | | read `DIFFICULTY_TARGET_*`, so they follow |

The web texts (`rules.js`, the Wallet's unlock times, Mine's "if the chain
stalls") and `rules.py` are updated.

### Publish-on-find and the displacement window (relay / fork-choice policy, `pof.rs`)

This is exactly the variant FAIRNESS.md simulated (section 2, "pof"): **runs
are relayed at find and eligible at validity.**

- **The time limit stays.**
  - A block is valid only if its run fits the limit at its stamp.
  - A node processes it only once it fits by the node's own clock, and once
    its stamp is within the 120 s consensus future limit.
  - The auction's shortest-run selection is unchanged: a shorter run fits
    sooner.
- **What changes is publication.** (Revised for one run per key: the first
  version relayed a run at find.)
  - A miner keeps searching privately and submits its best run **once**, a few
    seconds (default 5 s, `--submit-lead`) before it is due, stamped with the
    second it becomes valid (up to `MAX_HOLD_AHEAD_SECONDS` = 300 s ahead).
    It never signs a second run for the template.
  - The node does the cheap checks on arrival (parse, signature, one run per
    key, the per-source budget) and **queues the claim by its due time**
    (`hold_until`: `max(first second the run fits, stamp − 120)`; `None` for a
    stamp more than `MAX_HOLD_AHEAD_SECONDS` = 300 s ahead, rejected now).
    Restricted (public) RPC refuses a run due more than 30 s after it arrives
    (`RPC_SUBMIT_AHEAD_SECONDS`), so the miners' lead is capped at 25 s. **It does not relay the claim.** It is
    replayed when due (see "The replay queue" in [DOS.md](DOS.md)) and relayed
    only after the replay passed. Early relay of unreplayed claims would be a
    free amplifier for fake claims, and with one run per key it buys nothing:
    the window below is measured from eligibility, not from publication.
  - `block_verification_context::m_sm64_held` (relay a held run at once) is
    no longer set.
- **The window, ω = 30 s** (`POF_WINDOW_SECONDS`; 60 s in the first v0.3
  design). The auction-smoothness simulation (branch `auction-smoothness`,
  SMOOTH.md: 12 nodes, ±1.5 s clock skew, 2 s jittered propagation, 20-minute
  target) found 30 s better: the sniping gain over late publishing drops
  from +0.032 to +0.008, tip flips from 4.6 % to 2.4 %, splits are fewer,
  fairness (CV) is unchanged, and private chains get harder (P(z = 6) at
  33 %: 0.25 against 0.38). The freshness bound stays 60 s.
  - The first block on a parent that becomes eligible at a node opens the
    window, timed by that node's clock. A claim that went through the replay
    queue became eligible at `max(arrival, due)`, not when a (slow) worker got
    to it; that time is also what the freshness bound reads (review finding
    5). A block that came in a sync span counts as eligible at its own stamp
    (history: neither stale nor opening a window now).
  - A sibling replaces the node's current block at that height if all of
    these hold:
    - it becomes eligible inside the window;
    - it has strictly fewer frames, **or the same number of frames and a
      lower `cn_fast_hash(sm64_sig)`** (the deterministic tie-break: every
      node ends on the same block whatever the arrival order; in the
      simulation window-edge splits go from 0.8 % to 0; only the run's owner
      can change its signature, and grinding it only matters for exact
      ties, about 0.2-0.4 % of heights);
    - it has another miner key, i.e. another template and seed (copies of
      one run follow the restamp rule above, earliest stamp then lowest id);
    - the sibling has no counted equivocation evidence (the window never
      overrides the fork-choice penalty);
    - our block has no child yet. Inside the window it can't have one,
      because honest miners keep searching the height until it closes.

    The node reorganises to the sibling (`Blockchain::sm64_displaces` in
    the fork-choice condition, decided by `pof::Policy::displaces`).
  - After the window, the first block stays.
  - A sibling that could displace the tip is always worth a replay
    (`pof_candidate`, ahead of admit.rs's per-parent cap). Other siblings
    are handled as before.
  - Same-key runs follow the equivocation rule instead.
- **How nodes agree.**
  - The comparison is deterministic: same parent, another key, fewer frames,
    and the freshness of the stamps.
  - Only "inside the window" reads a node's clock. Nodes can disagree only
    about a sibling that arrives within propagation delay of the window's
    end, which is at most a one-block split, resolved by the next block like
    any race.
  - The window counts from the first eligible sibling, not from the current
    tip, so a chain of displacements can't extend it.
- **Why.**
  - The head start is gone (W 0 vs about 100-120 s today) when miners wait
    for the window.
  - Selfish mining stops paying up to α = 0.4. Today it pays from
    0.15-0.2 at γ = 0.5.
  - Shortest-run selection survives.
  - The costs: the tip flips in about 17 % of blocks during the window
    (nobody has built on the displaced block, so no work is lost), and private
    chains are slightly easier at ω = 120 (the first design took 60; 30
    now, see above).
  - Signatures make it safe. Without them a displacing run could be ground
    from someone else's published run, a variant one frame shorter.
- **Miners** (one run per key). The native miner (`automine`), the Rust and
  Python SDKs and the browser miner keep improving privately and submit the
  best run once, `submit_lead` seconds before it is valid (default 5,
  configurable: `--submit-lead`, `MinerConfig::submit_lead_secs`, Python
  `submit_lead=`, `miner.setLead(n)`); a run that is already valid goes out at
  once. Each records "signed for this seed" before signing and refuses a
  different run for a seed it already signed, across restarts: `automine
  --signed-file` (default `run/automine-signed.json`, last 256 seeds), the SDKs'
  `SignedStore` (`$SM64COIN_SIGNED_FILE` or `sm64coin-signed.json`), and
  `localStorage` `sm64coin.signedSeeds` in the browser (in-memory fallback).
  `--publish-on-find` and `--anytime-ahead` are gone. A miner that wants
  to keep searching for the window after a new block on the same parent can do so
  with a fresh key (a fresh template) at the same height; the key that
  signed does not sign again. Group mining (not on this branch): only the
  leader submits.

### The reorganisation cap (node policy, `pow/sm64pow/src/reorg.rs`)

A node refuses to reorganise more than **36 blocks** (12 h) deep. With the
cap, the depth an attacker can reverse is bounded exactly (fairness-research
LATE.md: z(0.1 %) becomes exactly N). The price: after a partition longer
than 36 blocks the two sides don't merge by themselves, and the refused
reorganisation is logged loudly (with the hash). The operator picks a side:
- `--sm64-max-reorg N` (0: unlimited), e.g. restart once with 0;
- or the unrestricted RPC `sm64_allow_reorg {"hash": "<a block of the other
  chain>"}`, which lets one reorganisation onto a chain holding that block;
  it happens when that chain's next block arrives.

While a reorganisation re-adds the disconnected blocks as alternatives,
nothing else is decided (no relay policy, no nested reorganisation).

### The freshness bound (relay policy, Δ = 60 s)

A block stamped more than 60 s before it became eligible at a node is **stale**
(`pof::stale`):
- it is accepted, because a longer chain always wins, so syncing nodes and
  partitions converge;
- it is **not relayed** (`m_sm64_stale`);
- while it has no child, a fresh sibling displaces it, whatever their lengths.

This caps back-dating at Δ per block: FAIRNESS.md section 8 found stamps
lagging real time by hours without a bound in the search-bound regime. It is
not consensus, because consensus can't see arrival times.

## What each person has to do

**Node operators**
- Install v0.3 and start with a **fresh data dir**. Move or delete
  `~/.sm64coin` (or your `--data-dir`), keeping the wallet files. The ROM is
  unchanged.
- Ports are unchanged. The node only talks to v0.3 peers.
- To keep a v0.2 node running alongside: give the two different data dirs and
  ports (`--p2p-bind-port`, `--rpc-bind-port`, `--zmq-rpc-bind-port`).
- The gateway / Pi: re-seed at launch. The first v0.3 node starts with
  `SOLO=1` and is then listed in `seeds.txt`.

**Miners**
- The native miner (`sm64coin-automine`), the browser miner and the GUI's
  local site (which uses the browser miner) all generate a key per template,
  pass it in `extra_nonce` and sign at submit. Update them; nothing to
  configure.
- `automine` submits its best run once, 5 s before it is due (see above).
- Blocks come every 20 minutes. With 4 threads a search takes about 250 s,
  one thread about 860 s, a browser worker about 1700 s, so all of them can
  now earn.
- `automine --save-block` now also saves `seed_hash` and `key_secret`.
  `--submit-saved` needs both.

**Bot authors** (see [../BOTS.md](../BOTS.md), "Signed proofs (v0.3)")
- Generate a key per template:
  - Rust SDK: `Keypair::generate()`; `run_miner` does it for you.
  - Python: `sm64coin.Keypair.generate()`.
- Request the template with `extra_nonce` = `64 || public key`, and no
  `reserve_size`.
- Play the run for that template, then `sign_proof(key, seed, proof)` and
  seal with the signature.
- Unsigned blocks, and blocks signed with a key the coinbase doesn't commit,
  are invalid on v0.3.
- Never submit two different runs of the same length for one template: that
  is equivocation.

**Tooling to update**
- `scripts/auction-test/websubmit.mjs` now seals the v0.3 way (the saved run
  carries `sig`; re-save with the current `automine --save-block`).
- The wallet WASM engine must be rebuilt from the new fork commit
  (`scripts/build-wallet-wasm.sh`; about 30 minutes, needs emsdk). The
  proof-id vectors (`web/wallet-wasm/test/run.sh`: 234 vectors) are unchanged
  and pass; the engine itself was **not rebuilt** here.
- The browser miner's WASM must be rebuilt (`scripts/build-wasm.sh`) for the
  new `miner_keypair` / `sign_proof` exports. Check them against
  `cargo run -p sm64pow --example sig_vectors`.

## Decided, and still open (for the owner)

Decided, in the "v0.3 CHOSEN PARAMETERS" block of `pow/sm64pow/src/rules.rs`:
- target 1200 s;
- `decay_grace` 0, `decay_halving` 60, `start_halvings` 20;
- `POF_WINDOW_SECONDS` 60;
- `FRESHNESS_SECONDS` 60;
- `MAX_HOLD_AHEAD_SECONDS` 300 (was 3600: far-future claims could fill the
  replay queue for an hour), `RPC_SUBMIT_AHEAD_SECONDS` 30;
- `launch_timestamp` 1795651200 (2026-11-26 00:00:00 UTC), applied on
  mainnet only (test networks run before it);
- the restart delays stay as scaled (4 h base);
- the coinbase lock, 72 blocks;
- the fork-choice penalty (1.5 blocks, evidence counted up to depth 2).

Open:

1. **Seed nodes** for launch (`seeds.txt`), and when to move the Pi.
2. The replay queue's defaults (`--sm64-replay-threads`, per-source share,
   fairness half-life, the invalid-source penalty): measured in
   [DOS.md](DOS.md), not tuned.
3. The miners' `submit_lead` default (5 s): short enough that a node's replay
   at due time is not the bottleneck, long enough for propagation.

## How it was tested

- Unit tests:
  - `sign::tests`: round trip; determinism; wrong key, wrong proof, wrong
    length and wrong template; flipped bits; non-canonical `r + l` / `c + l`;
    miner key parsing, including identity and small-order keys.
  - `equivocation::tests`: shorter runs supersede only while held; late
    shorter and longer runs are ignored; equal length is evidence, which
    verifies and round-trips; forged evidence (another key, or an attacker's
    own key over our seed) is refused; template parent choice.
  - Signed sealing in `pow/miner` (`rpc::tests`), the SDKs, and the web
    `minerkey.test.mjs`.
- Cross-implementation vectors: `cargo run -p sm64pow --example sig_vectors`.
  Python reproduces public key, extra nonce, `proof_id` and signature byte
  for byte (`python/tests/test_sign.py`, 16 vectors over raw, run-length
  and xz).
- Real blocks (`pow/sm64pow/tests/signed.rs`, on v0.2 mainnet blocks 1-34,
  `fixtures/mainnet_v02.jsonl`):
  - each block is treated as if its template had committed a key, and signed;
  - the four cheapest edits of each, 136 variants: 73 are valid runs
    unsigned, and every block has at least one;
  - **all 136 are rejected by the signature check, with zero replays**,
    whether the miner's signature is copied or the attacker signs with its own
    key. The check takes about 170 µs;
  - the real blocks verify with the same verdicts as unsigned v0.2
    verification.
- The replay layers are unchanged (`proof_id` vectors, codecs, `chain`,
  `dos`, `preverify` tests).
- Python and the WASM web miner (`wasm-pack --target nodejs` build) reproduce
  the Rust signatures for `sig_vectors` exactly. `cargo check --target
  wasm32-unknown-unknown` passes for `pow/webminer`.

### The private network (2026-11-25, fork `hardfork-v0.3` 3bbb414dc)

The setup was two `monerod` nodes on 127.0.0.1, A (`--sm64-solo`) and B, each
`--add-exclusive-node` to the other, on mainnet settings, so the **v0.3
genesis** `cbd56c9b…` (the v0.2 genesis was `baa56b55…`).

1. **Network separation.** A v0.2 node (dos-hardening build) pointed at A was
   refused at the handshake: `WRONG NETWORK AGENT CONNECTED!
   id=b882ecca-…` on A. The v0.2 node stayed on its own genesis.
2. **Two different-key runs for block 1.** Two `automine --save-block`
   searches (2 threads each) gave L, 4,231 frames (key `ff6c4f15…`), and S,
   3,508 frames (key `6fdb1f35…`).
   - L submitted to A: accepted (78 ms) and relayed to B.
   - 10 s later, against A:
     - S with a zero signature: refused, *"the proof's signature does not
       verify with the coinbase's miner key"*, no replay (0.8 ms);
     - S signed by another key: refused, no replay (0.7 ms);
     - **S, signed: accepted, and it displaced L on A and on B** (`block 59c5…
       displaces the tip 30ef…`, `REORGANIZE … SUCCESS`: the publish-on-find
       window);
     - four third-party variants of S (last byte ^01/^80/^ff, dropped) with
       S's signature copied: not replayed (0.8-0.9 ms each);
     - **S's miner signing an equal-length variant: equivocation.** A logged
       the evidence and relayed it; B logged *"equivocation evidence from
       127.0.0.1:27480"*. `get_block_template` on both nodes then built on
       the genesis block instead of the equivocated tip.
3. **Mining around the equivocator.** `automine` (4 threads,
   publish-on-find):
   - mined a clean sibling C1 of S (3,712 frames, published at find, stored as
     an alternative block);
   - the next template built on C1, the clean sibling (`choose_parent`);
   - its block 2 (2,817 frames) made C1's chain longer. Both nodes
     reorganised, **orphaning the equivocator's S**.
   - The reward was 1,125.8 SM64 per block, 4× v0.2's per 5-minute block,
     the same per day.
4. **Fresh sync.** A third node C synced the 3 blocks from A and replayed
   the signed blocks (`Synced 3/3`, every proof accepted).

Not exercised end to end:
- A pending run held and relayed before it was valid. Every run found here
  was already valid at difficulty 1; the path is unit-tested in `hold.rs`.
- The freshness bound's relay suppression (unit-tested in `pof.rs`).

Reproduce: `pow/miner/examples/v03_e2e.rs` (`SAVED.json URL [submit]`) on blocks
saved by `automine --save-block`.

### The private network, re-run for one run per key and the replay queue (2026-11-25)

Three local nodes (A `--sm64-solo`, B, C, each `--add-exclusive-node` to A, A to both) running the daemon
with the replay queue; two `automine --save-block` runs for block 1 with different keys: L, 4,277 frames,
S, 3,957 frames.

- **Honest propagation.** L submitted to A: accepted in 52 ms (the replay ran on the RPC thread outside the
  lock); B and C had it queued, replayed and added 54 ms after A (relay happens after the replay: a
  3,740-frame block in the first run, 53 ms). Well under 1 s at difficulty 1.
- **Displacement.** S (another key, strictly fewer frames, inside the window) displaced L on A and, after
  relay, on B and C (`REORGANIZE SUCCESS`, 54-61 ms apart).
- **Same-key second run.** The miner's own equal-length variant of S, signed: A logged the equivocation,
  B and C logged "equivocation evidence from 127.0.0.1:...", relayed. The 4 third-party variants with a
  copied signature and the unsigned / wrong-key blocks were refused without a replay (0.7-0.9 ms).
  The shorter / longer second run cases are covered by unit tests (`equivocation::tests`) and by
  `tests/signed.rs` on real blocks: 12 templates x 4 other runs (variants and a truncated proof): all
  evidence, the real blocks still valid.
- **Miners.** `automine`, the SDKs and the browser miner submit once before due: unit-tested (timing, signed-seed
  store across restarts, a throwing `localStorage`), **not demonstrated live** here: a run found before it is
  valid needs a chain whose limit has not yet grown to the run's length, and the local rh controller did not
  find block 2 in 40 minutes.
- Not re-run: a fresh third node syncing the chain (sync is unchanged: preverify).

### Known gaps

- The wallet binaries and the wallet WASM engine must be rebuilt against
  this fork commit: new genesis, block field and emission.
- A displaced block that this node already knew by seed is not stored as an
  alternative block (admit.rs skips it). It comes back if a longer chain is
  built on it.
- The replay queue replays a due claim only if it could matter (extends the
  tip, is strictly shorter than our block at that height inside the window, or
  is the preferred copy of it). An unasked sibling of the tip that can't
  displace it is dropped on arrival and not stored; if a peer builds on it,
  its child arrives as an orphan and the pair comes in a sync span.
- Restart state is rebuilt from the chain (`sm64_note_history`): the last 8
  blocks' runs are their templates' claims again and the tip is eligible at
  its stamp. Claims for templates whose block never made our chain, and
  queued claims, are lost at a restart (the sender's peers still have them).
- Evidence follow-ups: evidence is not included in sync responses (only sent
  with relayed blocks and on connect), and relay doesn't check that the
  accused block's parent is one we know.
