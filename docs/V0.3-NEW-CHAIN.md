# SM64Coin v0.3: a new chain with signed proofs

v0.3 starts a **new chain**: a new genesis block and a new network identity.
The v0.2 chain is not continued; its coins and blocks don't carry over.
There is no activation height and no old-rule code path: the new rules apply
from block 1. What changes from v0.2:

- **consensus**:
  - **signed proofs**;
  - a **20-minute block time** (v0.2: 5 min), with emission per day unchanged;
  - restart delays scaled with it;
- **relay and fork-choice policy**:
  - **publish-on-find** with a 60 s **displacement window**;
  - the **equivocation rule**;
  - a 60 s **freshness bound**.

The parameters are in one marked place: `STAR_CYCLE`'s "v0.3 CHOSEN
PARAMETERS" block and the constants below it in `pow/sm64pow/src/rules.rs`.

The reasons are in the fairness research, `pow/tools/auction/headstart/FAIRNESS.md`
on branch `fairness-research` (9ce5c91).

## Why

Every SM64Coin block's run can be changed a little and still be valid. Flip
or drop the proof's last byte and the last 1-13 inputs differ, but the star
still lands on the same frame. The seed does not cover the proof, so the
variant is a valid block with a new id. On the v0.2 mainnet **all 34 blocks**
have such a variant among the four cheapest edits (73 of 136 edits are
valid). [DOS.md](DOS.md) has the measurements.

v0.2.9's relay policy (`admit.rs`) stops variants from costing nodes replays.
Two problems are left, and no relay policy can fix them:

- **Fork-race griefing.** Anyone who sees block A first can race a free
  variant A' to some miners and split the network for a block.
- **A fork rooted at a variant** that spans more than one sync batch does not
  reorganise ([DOS.md](DOS.md), "What is left" 3).

Signing removes both at the root, because only the miner can make another
valid run for its template. The fairness research found that the
alternatives either don't help or make things worse:

- Content-based tie-breaks (lowest pads, fewest buttons, lowest hash) are
  grindable by spamming variants.
- Slow decay was measured and rejected.

See `pow/tools/auction/headstart/RESULTS.md` and `SLOWDECAY.md` on the
research branches `headstart-research` / `headstart-research-slowdecay`.

The owner chose a chain reset over an activation height. One coordinated
restart is simpler than carrying two rule sets forever.

## What changes

### Signed proofs (consensus)

1. **The miner key goes in the coinbase.** For each template, the miner
   generates a throwaway key pair. This is Monero's key format, an ed25519
   scalar and point, and is never the wallet's spend key. The miner asks
   for the template with `get_block_template {"wallet_address": ..,
   "extra_nonce": "64" + hex(public key)}`.
   - The daemon writes the nonce into the coinbase `tx_extra` as a
     `TX_EXTRA_NONCE` field. This is Monero's existing mechanism; pools use
     it for worker nonces.
   - The first byte `0x64` tags the content as a miner key, followed by the
     32-byte key. Pools may append more bytes.
   - `reserve_size` must be 0 or omitted, because Monero refuses both.
   - The seed is `cn_fast_hash` of the hashing blob with the timestamp zeroed.
     The hashing blob contains the merkle root, which covers the miner tx and
     its extra. So the seed, and with it the pokes, already commits the key:
     **one template, one key**.
   - The key must therefore be chosen before the run is played, and the same
     extra nonce must be used for every template request belonging to that
     run.
2. **The block carries a signature.** The new last field of the block blob is
   `sm64_sig`, 64 bytes. It is a Monero signature (`crypto::generate_signature`
   / `check_signature`: Schnorr on ed25519 with Keccak, `c || r`) by the
   coinbase key over:

   ```
   keccak256("sm64coin proof signature v1" || seed || proof_id(sm64_proof) || frames as u32 LE)
   ```

   `frames` is the proof header's claimed length.
3. **Nodes check it before any replay** (`chain::verify_signed_block` /
   `sm64pow_verify_signed_block`). The block is **invalid** if any of these
   holds:
   - the coinbase's first extra nonce does not commit a valid key (canonical,
     not small order, torsion-free);
   - the signature does not verify (both scalars must be canonical, and `c`
     non-zero);
   - the signature signs another seed, proof or length.

   The check takes about 0.1-0.2 ms, most of it `proof_id` (it decodes a
   stateless proof), and no replay. The sync pre-pass stops at the first bad
   signature. A held block's signature is checked before it can displace a
   held run of the same template.

Design decisions:

| question | decision | why |
|---|---|---|
| key type | Monero's own Schnorr signatures, byte-compatible with `crypto::check_signature`; implemented in Rust (`pow/sm64pow/src/sign.rs`, curve25519-dalek + Keccak) | No new signature scheme and no new C++ dependency: consensus stays in Rust, and stock Monero code can check the same signatures. curve25519-dalek is pure Rust and already in the workspace (the leaderboard), so the browser miner signs in WASM. The Python SDK has a pure-Python port, with no new dependency. |
| strictness | canonical `c` and `r`, `c != 0`, commitment not the identity; key canonical and torsion-free | A third party can't turn a valid signature into another valid one (`r + l`), so it can't mint a new block id. The miner picks its key, so the strict key rules cost honest miners nothing. |
| signing nonce | deterministic: `k = reduce512(keccak512("sm64coin signing nonce v1" ‖ secret ‖ msg ‖ ctr))` | Re-signing the same run gives the same signature, so the same block id. No RNG is needed at signing time. Verification doesn't care how `k` was chosen. |
| what is signed | seed, `proof_id`, frames | The **seed** binds the signature to the template, timestamp excluded, so restamping a block keeps its signature. **`proof_id`** is what the block id already commits to, and it is unchanged when the daemon re-encodes a stateless proof at `submit_block`, which signing the raw bytes would break. **Frames** let equivocation evidence compare lengths without the proofs. |
| key location | the coinbase extra nonce (`0x64` ‖ key), not a new `tx_extra` tag | Monero already lets a miner choose it (`get_block_template extra_nonce`), so it needs no change to Monero's tx-extra parser or the template RPC. The daemon's computed seed already covers it. |
| signature location | a new block field `sm64_sig` after `sm64_proof`, not inside the proof blob | The proof format, codecs, `proof_id` and their test vectors are unchanged. The signature is visible on its own in JSON (`"sm64_sig"`), and the fixed size leaves no length games. |
| in the block id? | **yes**: id = `cn_fast_hash(hashing blob ‖ proof_id ‖ sm64_sig)` | Third parties can't change the signature, and honest re-signing is deterministic, so including it creates no new ids. Excluding it would make it a witness. Then a garbage-signature copy would share the honest block's id, which risks poisoning id-keyed caches: "already have", invalid-block lists, requested-object tracking. |
| key per template | automatic, throwaway, generated by the miner | It is not the wallet key, so a leaked key costs nothing beyond that template. |

**Group mining** (the `group-mining` branch, not merged): the leader
generates the template key and shares the **secret** with its full-trust
group, so any member can sign and submit a run for the group template.
- Rust SDK: `run_miner_keyed(bot, cfg, &mut |round| Ok(Keypair::from_secret(&shared)?))`.
- Native miner: `Daemon::template_for(address, key)`.
- Python: `Keypair(secret)` passed as `next_key` to `run_miner`.
- Web: `minerkey.js` takes a key object.

The group branch needs these calls:
1. Leader: `Keypair::generate()`, then `get_block_template` with its
   `extra_nonce`.
2. Leader: share `{template blob, seed, secret}`.
3. Member: `sign_proof(key, seed, proof)`, then `seal_block`.

Members must never sign two different runs of the same length (see below);
the group should agree on one submitter.

### The new block field

```
block blob = header || miner_tx || tx_hashes || varint(len) || sm64_proof || sm64_sig (64 bytes)
```

- Templates and the genesis block carry 64 zero bytes. A template blob
  therefore ends with `00` (the empty proof) plus 64 zero bytes.
- To seal, strip those 65 bytes, set the timestamp, and append
  `varint(len(proof)) || proof || sig`. The helpers are
  `sm64pow::mining::seal_block` (Rust), `sm64coin.daemon.seal` (Python) and
  `web/src/lib/block.js seal` (JS).
- `proof_id` itself is unchanged, and so are its vectors in
  `web/wallet-wasm/test`.
- Block ids change, because they now commit to the signature.
- Seeds are computed the same way, but every template now has a different
  one, because each contains its miner key.

### The equivocation rule (relay policy, `pow/sm64pow/src/equivocation.rs`)

With signing, "same key" and "same template" (same seed) are the same thing.
For a template:

- **Before its block is valid** (held until the limit fits): the miner may
  submit any number of **strictly shorter** runs. Each replaces the held one
  (`held_replaces`; the daemon's hold map already keeps the run that fits
  sooner). This is the auction working and is never misbehaviour.
- **After a block for the template is in our chain**, another run for it
  arrives as an alternative block at the same height (`judge_sibling`, called
  from `sm64_skip_alt`):
  - the same run (same `proof_id` and length): ignored;
  - a bad signature: ignored (invalid);
  - **strictly shorter: ignored**, with no penalty and no tip takeover.
    Otherwise a miner could drip-feed late overrides of its own block;
  - **strictly longer: ignored** (see below);
  - **the same length, a different run: equivocation.** An honest miner only
    signs strictly shorter runs, so two signed runs of one length prove a
    deliberate split. The node keeps compact **evidence**: 272 bytes (tag,
    seed, key, and two `(proof_id, frames, sig)`), verifiable without the
    blocks. It logs the evidence and **refuses to build on that block while
    it is childless**: `get_block_template` without `prev_block` builds on a
    clean sibling at the tip's height, or else on the tip's parent
    (`choose_parent`). The equivocator's block then loses the race once a
    sibling gets a child.

**A deviation from the design list.** The list says a different
*equal-or-longer* run is evidence. Longer runs are not evidence here
(`LONGER_IS_EVIDENCE = false`), because honest miners produce that pattern:

1. A miner submits run A, then a shorter A' before either is valid.
2. A' becomes valid first and spreads.
3. A node that held A and had not yet seen A' when A became due relays A.
4. A third node then sees A, which is longer, after A'.

Equal lengths never happen honestly. Turning longer runs on needs a margin
rule, for example "longer by more than the hold slack".

**The evidence message**, `NOTIFY_SM64_EVIDENCE`, levin id
`BC_COMMANDS_POOL_BASE + 12`, one `std::string evidence` of 272 bytes.
- A node that finds equivocation (in `sm64_skip_alt`) or receives new valid
  evidence queues it in Rust (`equivocation::Policy::take_outbox`).
- `core::on_idle` relays the queue to every public peer.
- The handler drops wrong-size messages and verifies the rest in Rust (two
  signatures, `sm64pow_evidence_received`).
- Evidence counts against a template only if its key is the one that
  template's coinbase commits. A node records the key when it checks the
  block's signature, so a forged key over someone else's seed does nothing.

It is modelled on `NOTIFY_SM64_BOARD`, about 60 lines in the fork.

A reserve option, not implemented: a consensus burn of the equivocator's
locked coinbase, via evidence included in a later block.

### The 20-minute block (consensus)

`Rules::target_seconds` is 1200, and so are `DIFFICULTY_TARGET_V1` / `_V2`
(v0.2: 300).

Why: FAIRNESS.md section 0 and section 5.
- What decides who wins is the latency of one search, which is 18-106 M
  emulated frames with a hard floor of about 18 M.
- A miner earns its share while its mean search time is under about 1.5× the
  block interval, and gets nothing beyond about 2×.
- At 300 s only multi-thread native searches are fair (about 250 s on 4
  threads). One-thread natives take about 860 s and browser workers about
  1700 s, and both earn 0.
- A longer target is the only rule lever that moves this cliff: 600 s makes
  one-thread natives fair, 900-1200 s browsers. A grace period does not: it
  is either a longer block or nothing.
- Per-block security is unchanged.

What follows from it:

| | v0.2 (5 min) | v0.3 (20 min) |
|---|---|---|
| emission per block | `(supply − generated) >> 16` | `>> 14`, 4× per block, **the same per day**. Monero's factor `20 − (minutes − 1)` doubles per extra minute; at 20 min it would be 1, half the supply in one block, so the fork sets 14 explicitly (`get_block_reward`, with a `static_assert` on the target). The tail emission is per minute, so it is unchanged per day |
| coinbase unlock | 4 blocks ≈ 20 min | 4 blocks ≈ 80 min (unchanged in blocks: reorg depth is what matters) |
| wallet spendable age | 10 blocks ≈ 50 min | 10 blocks ≈ 200 min |
| restart delay | 1 h + 60 s/point, at most 2 h (12 block times) | **4 h + 240 s/point, at most 8 h** (still 12 block times, so a slow network with difficulty pinned at 1 doesn't throw its progress away; **open**: 4 h is a long stall) |
| limit curve | `decay_grace` 0, `decay_halving` 60 s, `start_halvings` 20, cap 36,000 frames (20 min of play), floor 600 | **unchanged**; FAIRNESS.md section 9 and SLOWDECAY.md, and the "no grace" test is kept |
| what the retarget settles at | difficulty ~2^4-2^8 | ~2^16 for ~2,500-frame winning runs: where the shortest finished run fits about 1,200 s after the parent. At difficulty 1, a network too slow for its target, the limit reaches its 20-minute cap exactly one target after the parent |
| locked-tx deltas, wallet time estimates, the block-rate warning | | read `DIFFICULTY_TARGET_*`, so they follow |

The web texts (`rules.js`, the Wallet's unlock times, Mine's "if the chain
stalls") and `rules.py` are updated.

### Publish-on-find and the displacement window (relay / fork-choice policy, `pof.rs`)

This is exactly the variant FAIRNESS.md simulated (section 2, "pof"): **runs
are relayed at find and eligible at validity.**

- **The time limit stays.**
  - A block is valid only if its run fits the limit at its stamp.
  - A node processes it only once it fits by the node's own clock, and once
    its stamp is within the 120 s consensus future limit.
  - The auction's shortest-run selection is unchanged: a shorter run fits
    sooner.
- **What changes is publication.**
  - A miner submits a run as soon as it finds it, stamped with the second it
    becomes valid (up to `MAX_HOLD_AHEAD_SECONDS` = 3600 s ahead).
  - The node validates it (signature, then replay at its stamp), holds it,
    and **relays it at once**, where v0.2 relayed it only when due. Every
    node therefore sees the pending runs.
  - What changes in `hold_until`: it returns
    `max(first second the run fits, stamp − 120)`, and refuses (returns
    `None`) a stamp more than 3600 s ahead. The daemon's old "stamped beyond
    the future limit is not held" check is gone.
  - A held run is relayed via a new flag, `block_verification_context::m_sm64_held`.
- **The window, ω = 60 s.**
  - The first block on a parent that becomes eligible at a node opens the
    window, timed by that node's clock.
  - A sibling replaces the node's current block at that height if all of
    these hold:
    - it becomes eligible inside the window;
    - it has strictly fewer frames;
    - it has another miner key, i.e. another template and seed;
    - our block has no child yet. Inside 60 s it can't have one, because
      honest miners keep searching the height until the window closes.

    The node reorganises to the sibling (`Blockchain::sm64_displaces` in
    the fork-choice condition, decided by `pof::Policy::displaces`).
  - After the window, the first block stays.
  - A sibling that could displace the tip is always worth a replay
    (`pof_candidate`, ahead of admit.rs's per-parent cap). Other siblings
    are handled as before.
  - Same-key runs follow the equivocation rule instead.
- **How nodes agree.**
  - The comparison is deterministic: same parent, another key, fewer frames,
    and the freshness of the stamps.
  - Only "inside the window" reads a node's clock. Nodes can disagree only
    about a sibling that arrives within propagation delay of the window's
    end, which is at most a one-block split, resolved by the next block like
    any race.
  - The window counts from the first eligible sibling, not from the current
    tip, so a chain of displacements can't extend it.
- **Why.**
  - The head start is gone (W 0 vs about 100-120 s today) when miners wait
    for the window.
  - Selfish mining stops paying up to α = 0.4. Today it pays from
    0.15-0.2 at γ = 0.5.
  - Shortest-run selection survives.
  - The costs: the tip flips in about 17 % of blocks during the window
    (nobody has built on the displaced block, so no work is lost), and private
    chains are slightly easier at ω = 120, so ω stays at 60.
  - Signatures make it safe. Without them a displacing run could be ground
    from someone else's published run, a variant one frame shorter.
- **Miners.** `automine` now publishes at find (`--publish-on-find`, default
  on) and again for every strictly shorter run of the same template. The same
  key replaces the held one; a fresh key per template keeps searching the
  height. The browser miner still submits shortly before validity, which is
  compatible but loses the head-start benefit. **Open**: make it publish at
  find too, and keep its searches running for 60 s after a new block on the
  same parent.

### The freshness bound (relay policy, Δ = 60 s)

A block stamped more than 60 s before it became eligible at a node is **stale**
(`pof::stale`):
- it is accepted, because a longer chain always wins, so syncing nodes and
  partitions converge;
- it is **not relayed** (`m_sm64_stale`);
- while it has no child, a fresh sibling displaces it, whatever their lengths.

This caps back-dating at Δ per block: FAIRNESS.md section 8 found stamps
lagging real time by hours without a bound in the search-bound regime. It is
not consensus, because consensus can't see arrival times.

**Wallets.**
- **CLI / GUI wallets (wallet2):** a v0.2 wallet cache is refused against a
  v0.3 daemon with "Genesis block mismatch". Keep the `.keys` file, delete the
  cache file (the one without an extension), and restore from height 0.
- **Web wallet:** the IndexedDB record is now tagged with the chain id
  `v0.3:<genesis hash>`. A record saved on v0.2 (no tag) opens keys-only and
  rescans from height 0, automatically. A desktop cache imported by hand is
  trusted as given.

## What each person has to do

**Node operators**
- Install v0.3 and start with a **fresh data dir**. Move or delete
  `~/.sm64coin` (or your `--data-dir`), keeping the wallet files. The ROM is
  unchanged.
- Ports are unchanged. The node only talks to v0.3 peers.
- To keep a v0.2 node running alongside: give the two different data dirs and
  ports (`--p2p-bind-port`, `--rpc-bind-port`, `--zmq-rpc-bind-port`).
- The gateway / Pi: re-seed at launch. The first v0.3 node starts with
  `SOLO=1` and is then listed in `seeds.txt`.

**Miners**
- The native miner (`sm64coin-automine`), the browser miner and the GUI's
  local site (which uses the browser miner) all generate a key per template,
  pass it in `extra_nonce` and sign at submit. Update them; nothing to
  configure.
- `automine` publishes at find (see above).
- Blocks come every 20 minutes. With 4 threads a search takes about 250 s,
  one thread about 860 s, a browser worker about 1700 s, so all of them can
  now earn.
- `automine --save-block` now also saves `seed_hash` and `key_secret`.
  `--submit-saved` needs both.

**Bot authors** (see [../BOTS.md](../BOTS.md), "Signed proofs (v0.3)")
- Generate a key per template:
  - Rust SDK: `Keypair::generate()`; `run_miner` does it for you.
  - Python: `sm64coin.Keypair.generate()`.
- Request the template with `extra_nonce` = `64 || public key`, and no
  `reserve_size`.
- Play the run for that template, then `sign_proof(key, seed, proof)` and
  seal with the signature.
- Unsigned blocks, and blocks signed with a key the coinbase doesn't commit,
  are invalid on v0.3.
- Never submit two different runs of the same length for one template: that
  is equivocation.

**Tooling to update**
- `scripts/auction-test/websubmit.mjs` still seals the v0.2 way, and its
  saved-run format has no key.
- The wallet WASM engine must be rebuilt from the new fork commit
  (`scripts/build-wallet-wasm.sh`). Re-run `web/wallet-wasm/test`; any
  block-id vectors change.
- The browser miner's WASM must be rebuilt (`scripts/build-wasm.sh`) for the
  new `miner_keypair` / `sign_proof` exports. Check them against
  `cargo run -p sm64pow --example sig_vectors`.

## Decided, and still open (for the owner)

Decided, in the "v0.3 CHOSEN PARAMETERS" block of `pow/sm64pow/src/rules.rs`:
- target 1200 s;
- `decay_grace` 0, `decay_halving` 60, `start_halvings` 20;
- `POF_WINDOW_SECONDS` 60;
- `FRESHNESS_SECONDS` 60;
- `MAX_HOLD_AHEAD_SECONDS` 3600.

Open:

1. **Restart delays**: they are scaled ×4 with the block time (4 h base),
   which is my choice, not yet the owner's.
2. **`launch_timestamp`**: the new chain's launch, which no block but the
   genesis block may be stamped before. It is v0.2's (2026-11-22) until the
   launch date is picked.
3. **Seed nodes** for launch (`seeds.txt`), and when to move the Pi.
4. **Longer runs as evidence** (`LONGER_IS_EVIDENCE`), and whether to
   implement the P2P evidence message before launch.
5. **The browser miner's publish-on-find**, and the miners' wait-for-window
   default (see above).

## How it was tested

- Unit tests:
  - `sign::tests`: round trip; determinism; wrong key, wrong proof, wrong
    length and wrong template; flipped bits; non-canonical `r + l` / `c + l`;
    miner key parsing, including identity and small-order keys.
  - `equivocation::tests`: shorter runs supersede only while held; late
    shorter and longer runs are ignored; equal length is evidence, which
    verifies and round-trips; forged evidence (another key, or an attacker's
    own key over our seed) is refused; template parent choice.
  - Signed sealing in `pow/miner` (`rpc::tests`), the SDKs, and the web
    `minerkey.test.mjs`.
- Cross-implementation vectors: `cargo run -p sm64pow --example sig_vectors`.
  Python reproduces public key, extra nonce, `proof_id` and signature byte
  for byte (`python/tests/test_sign.py`, 16 vectors over raw, run-length
  and xz).
- Real blocks (`pow/sm64pow/tests/signed.rs`, on v0.2 mainnet blocks 1-34,
  `fixtures/mainnet_v02.jsonl`):
  - each block is treated as if its template had committed a key, and signed;
  - the four cheapest edits of each, 136 variants: 73 are valid runs
    unsigned, and every block has at least one;
  - **all 136 are rejected by the signature check, with zero replays**,
    whether the miner's signature is copied or the attacker signs with its own
    key. The check takes about 170 µs;
  - the real blocks verify with the same verdicts as unsigned v0.2
    verification.
- The replay layers are unchanged (`proof_id` vectors, codecs, `chain`,
  `dos`, `preverify` tests).
- The private two-node network: see the testnet section below.
